# SaaS 架构改造需求规格说明书

## 1. 引言

### 1.1 功能概述

本项目旨在将现有的单租户医疗设备内容管理系统（CMS）改造为多租户 SaaS 架构。改造后系统将支持：
- **超级管理员层**：位于租户体系之上，管理所有租户账户、订阅和系统级配置
- **多租户架构**：每个租户（用户）拥有独立的数据空间、官网前台和管理后台
- **租户隔离**：通过 tenant_id 实现数据行级别隔离，确保租户数据安全
- **域名支持**：支持独立域名（tenant.example.com）和路径区分（example.com/tenant）两种访问方式

### 1.2 背景与目标

**当前状态**：
- 单租户架构，所有数据共享同一空间
- 仅有一套前台官网和后台管理系统
- 用户角色仅分为 admin 和 user，无租户概念

**改造目标**：
- 实现多租户 SaaS 架构，支持无限扩展租户
- 建立超级管理员体系，实现租户生命周期管理
- 每个租户拥有独立的官网前台和管理后台
- 保持现有功能的同时支持多租户隔离

### 1.3 关键利益相关者与用户

| 角色 | 职责 | 使用场景 |
|------|------|----------|
| 超级管理员 | 系统运营方，管理所有租户 | 创建/删除租户、查看系统统计、处理租户问题 |
| 租户管理员 | 租户的管理员用户 | 管理自己租户的官网内容、配置、用户 |
| 租户普通用户 | 租户的普通用户 | 查看官网内容，有限的后台操作权限 |
| 官网访客 | 最终用户 | 访问租户的官网前台页面 |

### 1.4 预期价值与收益

- **商业价值**：支持 SaaS 订阅模式，实现商业化运营
- **技术价值**：建立可扩展的多租户架构基础
- **用户价值**：每个租户拥有独立的品牌官网和管理系统

## 2. 需求

### 需求 001 - 超级管理员账户体系

**用户故事**：作为一名**超级管理员**，我希望**拥有独立于租户的超级管理员账户体系**，以便**管理整个 SaaS 平台的所有租户**。

**验收标准（EARS 格式）**：
1. 当系统初始化时，系统应自动创建一个默认超级管理员账户（superadmin/superadmin123）
2. 如果用户是超级管理员角色，则系统应允许其访问超级管理员后台
3. 当超级管理员登录时，系统应将其重定向到超级管理员后台而非租户后台
4. 系统应区分超级管理员角色（superadmin）和租户管理员角色（tenant_admin）
5. 系统应不支持超级管理员账户与租户的关联关系

### 需求 002 - 租户管理

**用户故事**：作为一名**超级管理员**，我希望**创建、编辑、删除租户**，以便**管理平台的租户生命周期**。

**验收标准（EARS 格式）**：
1. 当超级管理员创建租户时，系统应自动生成唯一的租户标识（tenant_id 和 tenant_code）
2. 如果租户被创建，则系统应自动为该租户创建默认管理员账户
3. 当超级管理员编辑租户时，系统应支持修改租户名称、状态、域名配置、订阅信息
4. 当超级管理员禁用租户时，系统应阻止该租户的所有用户登录
5. 当超级管理员删除租户时，系统应软删除租户及其所有关联数据
6. 系统应支持租户状态管理（活跃、禁用、待激活）

### 需求 003 - 租户订阅管理

**用户故事**：作为一名**超级管理员**，我希望**管理租户的订阅计划**，以便**实现 SaaS 商业化运营**。

**验收标准（EARS 格式）**：
1. 当超级管理员设置租户订阅时，系统应支持选择订阅计划（免费版、专业版、企业版）
2. 如果订阅过期，则系统应自动降级租户功能或禁用租户
3. 当订阅计划变更时，系统应记录变更历史
4. 系统应根据订阅计划限制租户的资源使用（如存储空间、用户数量）

### 需求 004 - 租户数据隔离

**用户故事**：作为一名**租户管理员**，我希望**我的租户数据与其他租户完全隔离**，以便**确保数据安全和隐私**。

**验收标准（EARS 格式）**：
1. 当任何业务数据被创建时，系统应自动关联当前租户的 tenant_id
2. 如果查询业务数据，则系统应自动过滤仅返回当前租户的数据
3. 当租户管理员访问数据时，系统应验证其只能访问本租户数据
4. 系统应在所有业务表（Image、PageConfig、ModuleConfig、ContentItem、LanguageText、SiteSetting、ContactSubmission）中添加 tenant_id 字段
5. 系统应不支持跨租户数据访问，除非是超级管理员

### 需求 005 - 租户独立前台官网

**用户故事**：作为一名**租户管理员**，我希望**拥有独立的官网前台**，以便**展示我租户的品牌和内容**。

**验收标准（EARS 格式）**：
1. 当访客访问租户官网时，系统应根据域名或路径识别租户
2. 如果租户被禁用，则系统应返回服务不可用页面
3. 当请求官网内容时，系统应仅返回该租户的配置和内容
4. 系统应支持通过子域名（tenant.example.com）访问租户官网
5. 系统应支持通过路径（example.com/tenant）访问租户官网
6. 系统应为每个租户提供独立的上传空间

### 需求 006 - 租户独立后台管理

**用户故事**：作为一名**租户管理员**，我希望**拥有独立的管理后台**，以便**管理我租户的官网内容和配置**。

**验收标准（EARS 格式）**：
1. 当租户管理员登录时，系统应将其重定向到租户后台而非超级管理员后台
2. 如果用户是租户管理员，则系统应限制其只能管理本租户的数据
3. 当租户管理员操作数据时，系统应自动关联当前租户的 tenant_id
4. 系统应为每个租户提供独立的管理后台界面
5. 系统应支持租户管理员管理本租户的用户（创建、编辑、删除）

### 需求 007 - 租户用户管理

**用户故事**：作为一名**租户管理员**，我希望**管理我租户的用户账户**，以便**分配不同的操作权限**。

**验收标准（EARS 格式）**：
1. 当租户管理员创建用户时，系统应自动将用户关联到当前租户
2. 如果用户属于某租户，则系统应限制其只能访问该租户的资源
3. 当租户管理员删除用户时，系统应软删除用户账户
4. 系统应支持租户内用户角色管理（管理员、编辑、查看者）
5. 系统应不支持用户跨租户访问

### 需求 008 - 超级管理员数据查看

**用户故事**：作为一名**超级管理员**，我希望**查看任意租户的数据**，以便**协助租户解决问题或进行审计**。

**验收标准（EARS 格式）**：
1. 当超级管理员选择查看某租户时，系统应允许其访问该租户的所有数据
2. 如果超级管理员切换租户上下文，则系统应更新当前操作的租户标识
3. 当超级管理员操作租户数据时，系统应记录审计日志
4. 系统应提供租户数据概览和统计功能

### 需求 009 - 租户域名配置

**用户故事**：作为一名**租户管理员**，我希望**配置我租户的访问域名**，以便**使用自定义域名访问官网**。

**验收标准（EARS 格式）**：
1. 当超级管理员配置租户域名时，系统应支持设置子域名和自定义域名
2. 如果配置了自定义域名，则系统应支持通过该域名访问租户官网
3. 当域名配置变更时，系统应支持 DNS 验证流程
4. 系统应为每个租户生成默认的子域名（基于 tenant_code）

### 需求 010 - 现有数据迁移

**用户故事**：作为一名**系统实施者**，我希望**将现有单租户数据迁移为默认租户数据**，以便**保持历史数据连续性**。

**验收标准（EARS 格式）**：
1. 当系统执行数据迁移时，系统应创建一个默认租户（tenant_code: default）
2. 如果存在现有业务数据，则系统应将其关联到默认租户
3. 当迁移完成后，系统应将现有管理员账户关联到默认租户
4. 系统应保留所有现有数据，不丢失任何历史记录

### 需求 011 - 认证与授权增强

**用户故事**：作为一名**系统用户**，我希望**JWT Token 中包含租户信息**，以便**系统正确识别我的租户上下文**。

**验收标准（EARS 格式）**：
1. 当用户登录时，系统应在 JWT Token 中包含 tenant_id 和 tenant_code
2. 如果 Token 中缺少租户信息，则系统应拒绝访问租户资源
3. 当超级管理员登录时，系统应在 Token 中标识其为超级管理员角色
4. 系统应支持超级管理员临时切换租户上下文

### 需求 012 - 审计日志

**用户故事**：作为一名**超级管理员**，我希望**记录所有关键操作的审计日志**，以便**追踪系统操作和合规审计**。

**验收标准（EARS 格式）**：
1. 当超级管理员操作租户数据时，系统应记录操作人、操作时间、操作内容
2. 如果租户数据被修改，则系统应记录修改前后的值
3. 当用户登录/登出时，系统应记录登录日志
4. 系统应支持审计日志查询和导出

## 3. 非功能需求

### 3.1 性能需求

1. 系统应支持至少 1000 个并发租户访问
2. 租户识别应在 50ms 内完成
3. 数据库查询应通过 tenant_id 索引优化

### 3.2 安全需求

1. 系统应确保租户数据严格隔离，无越权访问风险
2. 超级管理员操作应进行二次验证
3. 所有 API 请求应进行租户身份验证

### 3.3 可用性需求

1. 系统应支持 99.9% 的可用性
2. 租户禁用/启用操作应即时生效
3. 系统应提供数据备份和恢复机制

### 3.4 可扩展性需求

1. 系统架构应支持水平扩展
2. 新增租户不应影响现有租户性能
3. 系统应支持未来升级到 Schema 级别隔离

---

## 4. 约束与假设

### 4.1 技术约束

- 保持现有 Go + Gin + SQLite 技术栈
- 兼容现有 API 接口设计
- 支持渐进式迁移，不影响现有功能

### 4.2 业务假设

- 初期租户数量在可管理范围内
- 超级管理员由系统运营方担任
- 租户订阅计费系统后续实现

## 5. 术语定义

| 术语 | 定义 |
|------|------|
| 租户 (Tenant) | SaaS 系统中的一个独立用户组织，拥有独立数据和配置 |
| 超级管理员 (Superadmin) | 系统最高权限用户，管理所有租户 |
| 租户管理员 (Tenant Admin) | 租户内的最高权限用户，管理本租户 |
| Tenant ID | 租户的唯一数字标识符 |
| Tenant Code | 租户的唯一字符串标识符，用于域名和路径识别 |
| 多租户 (Multi-tenant) | 多个租户共享同一套系统实例的架构模式 |
